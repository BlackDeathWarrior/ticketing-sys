# CLAUDE.md

Guidance for working in this repo. Read `docs/IMPLEMENTATION_PLAN.md` for the phase plan, its reality check (what exists and what is missing), and `docs/adr/` for decisions. Channel research is in `docs/research/`.

## Commands

- `pnpm docker:up` runs the whole stack in Docker (web :8080, Orbit Desk :8081, API :3000); `pnpm docker:down` stops it. App images come from the root `Dockerfile` targets `api`, `worker`, `migrate`, `web`, `orbit-desk`.
- `pnpm dev` runs tsc --watch plus the API (`dist/main.js`) and worker (`dist/worker.js`); both come from `apps/api`.
- `pnpm demo:email` sends a customer email to the dev support mailbox.
- `pnpm sample:load` loads the fictional sample data (`scripts/sample-data/data.ts`) through the API; `pnpm e2e` runs the Playwright suite in `e2e/` against the running stack.
- `scripts/demo/garment-demo.ps1 start|stop|up|load|shop|storefront|status|reset|down` runs the Ethnic Threads demo (`start` brings up the stack, the shop's server and its site in one go and updates what changed since the last start: it builds the stack again when the platform code changed, runs the loader when its data changed, and restarts the shop's server when the shop's code or `.env` changed; `-Rebuild` and `-Load` force the first two; `stop` stops all of it and keeps the data) (ADR 0027, ADR 0028): the compose project `tms-garment` (`infra/docker-compose.garment.yml`, API :3200, Orbit Desk :8091) with the shop from the garment-web-scraper repository (branch `feat/shop`) in the folder next to this one. `pnpm garment:load` is the loader alone; `pnpm e2e:garment` runs `e2e/tests/garment` (skipped unless `GARMENT_URL` is set).
- `pnpm build` builds all packages (apps depend on `packages/*/dist`, so build after changing `shared` or `db`).
- `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:int` (needs Postgres, Redis, LiteLLM and `fake-providers`; see README). On Windows, where `@swc/core` rejects its cache folder, run them with `bash scripts/check-in-docker.sh [steps]` (a Linux container on the compose network). `pnpm e2e` accepts `CHROMIUM_PATH`. `pnpm kb:eval` reports knowledge-base recall@5 and `pnpm ai:eval` runs the AI golden conversations (including the red-team ones) against a running stack. CI also runs `pnpm audit`.
- `pnpm db:generate` after schema edits; commit the SQL in `packages/db/drizzle`. Hand-written SQL goes in `drizzle-kit generate --custom` migrations.

## Rules

- Mutations: one DB transaction containing the change + `AuditService.record` + `OutboxService.publish`. Never skip either. (`llm_calls` is a metrics log and the only exception; see ADR 0008.)
- Validate input with zod schemas from `packages/shared` via `ZodPipe`; add new contracts there.
- Routes are authenticated by default; add `@RequirePermission(...)` to every non-public route. New permissions go in `packages/shared/src/permissions.ts` and the role map there.
- A module only touches its own tables; use the owning module's service otherwise. The read-only `reports` module is the exception.
- In `apps/api` (API and worker entry points), injected classes must be value imports (Nest reads constructor metadata).
- Orbit Desk (`apps/orbit-desk`) is the product console (ADR 0005); new user-facing features go there. `apps/web` stays a barebones test console (no styling libraries). Customer-facing pages go in `apps/help-center` (served at `/help/`): the request form, the portal and the rating page. The request form's API is `apps/api/src/web-form` under `@Public()` routes that only ever create, never read a ticket back (ADR 0012); reading belongs to the portal (`apps/api/src/portal`, ADR 0019).
- `apps/orbit-desk` follows `docs/DESIGN.md`; keep its rules:
  - Tokens from `apps/orbit-desk/src/styles/tokens.css` only; never hard-code colors, radii or shadows.
  - Font weights 400 and 500 only. Radii 5px (buttons/inputs), 16px (cards), 32px (badges), 999px (nav pill).
  - Inset rim-light glows, never drop shadows. The cosmic gradient only on text and thin strokes.
  - Lavender `#9382ff` marks only links, focus, active states and "needs attention"; iris `#5046e4` fills at most one primary button per view.
  - No red/green/yellow: status is glyph shape, label and opacity. The one exception is connection health: the `StatusLight` component (tokens `--signal-*`), always with a text label (ADR 0016).
  - Check UI changes at ≈1440px and 390px with no horizontal scroll and no console errors.
- Add integration tests in `apps/api/test/*.int.test.ts` for new endpoints, and an E2E spec in `e2e/tests` for new user-facing flows. Sample data stays fictional (`example.*` domains). Background behaviour: start the worker in-process with `startWorker()` from `test/helpers.ts`.
- All LLM calls go through `LlmClientService` (`chat`/`embed` with a role), never a provider SDK directly. What "Add a model" offers is LiteLLM's model list (`llm/model-catalogue.ts`): a catalogue, not the provider's answer for a key, so only a real call says whether a model can be used (`LlmSettingsService.testModel`, run when a person asks, never by itself). A provider's `testModel` in `LLM_PROVIDER_INFO` should be a "latest" alias where the provider has one: dated names get retired. Errors from LiteLLM reach people through `litellmErrorReason` (the provider's own message, never a key). Credentials go through `SecretsService` (or LiteLLM for provider keys); no route may return a secret's value, and key fields need `settings:secrets` (ADR 0009). Channel settings come from `ChannelConfigService`, not `env` directly.
- AI actions run with `AI_CTX` (actor type `ai`) and are recorded in `ai_runs` through `AiRunsService`. AI replies go through `OutboundService.aiReply` (sent or `draft`), never straight to a channel. A draft on chat, WhatsApp or an app's request page (`api`) also sends the customer one automatic "a person will reply" message (`OutboundService.holdingReply`, author `system`, never counted as a first response; the AI's handover message is sent with `notice: true` and is not counted either): any new outcome that leaves a live customer without an answer must tell them so. An app learns that an answer is being written from `replying` on the integration ticket view (true only when the AI sends by itself). That handover message is sent by `HandoverHandler` after routing, so it can name the colleague (`handoverMessage`, once per handover, on web chat, WhatsApp, email and `api` tickets; a call hears it from the turn at once). Every approval decision carries a reason (`decideApprovalSchema.reason`, required for approve and reject) that is written for the customer: the follow-up passes it to the model as data (`<team_reason>`) and the customer is told the outcome and the reason in their channel, by a fixed message (`approvalOutcomeMessage`) if the model fails or nobody has picked the conversation up; a person is only left a note when they have taken the conversation over. The optional `note` is for colleagues and never reaches the model. An answer that settles the request ends with a fixed "anything else?" (`closingQuestion`, added in `apply()`, never written by the model). Change prompts only with a version bump in `apps/api/src/ai/prompts.ts`, and add a golden to `apps/api/test/evals/` for new behaviour (ADR 0011). Leave models that reason before they answer room to do it: `maxTokens` is a ceiling on reasoning plus answer, and a tight one returns nothing or half a JSON object. The integration tests talk to a running scripted model: after changing `apps/fake-providers`, test against your own build (`TMS_FAKE_HOST`, see `scripts/check-in-docker.sh`), or a new scripted behaviour is silently not there.
- Company-system tools run only through `ToolGatewayService.invoke` (ADR 0013): it binds the customer (`customerArg` is filled from the ticket, never the model), validates arguments, and records `tool_calls`. `transactional` tools create an approval instead of running; the worker runs approved calls (`executeApproved`) and `AiAgentService.followUp` tells the customer. MCP servers are reached over streamable HTTP with `assertPublicUrl` on every call; `TOOL_PRIVATE_HOSTS` lists compose hosts allowed to be private. Tool tokens are secrets `tool.<slug>.token`.
- Teams own their tickets (ADR 0031): every route that changes a ticket or speaks for its team carries `@ActsOnTicket()` (`tickets/ticket-access.ts`, the check is `canActOnTeam`); reading and internal notes stay open to everyone with `ticket:read`. A new route of that kind needs the decorator. Approvals are decided by `approvals.team_id` (the tool's `approverTeamId`, else the ticket's team; `canDecideApproval`), and lists and notifications are scoped the same way. Team admins (`team_members.role`) manage their team's members; `admin` is the super admin. Priority rules (ADR 0032, `PriorityRulesService`) set a ticket's priority at creation and only raise it afterwards.
- Who answers is the conversation's `controller` plus the ticket's `handling` (ADR 0014): change them together, in one transaction (`TicketsService.setHandling` next to `ConversationsService.setController`). Handovers go through `HandoverService.createInTx` (it emits `handover.requested`; the worker routes, notifies and writes the context pack). Take-over/hand-back are `HandoverService` methods; don't set controllers to `human`/`ai` elsewhere.
- SLA timers change only through `SlaService.reconcile` (idempotent, driven by ticket events) and `sweep`; business-time maths lives in `apps/api/src/sla/business-time.ts`. Routing goes through `RoutingService.route`. Notifications go through `NotificationsService.notify` with a dedupe key; marking your own notifications read is the one unaudited write besides `llm_calls`. A person's own settings (`users.preferences`, `userPreferencesSchema`: the notification sound) are read and written only through `/me/preferences`, for the caller alone; the sound itself is generated in the browser (`apps/orbit-desk/src/lib/sound.ts`), there is no audio file.
- Custom tools (ADR 0017) are `tools` rows with an `http` definition under the built-in `custom` holder; they run through `ToolGatewayService` like MCP tools, over `callHttpTool` (SSRF check on every call, redirects refused). Their routes need `tool:create`, which admins can grant to roles through `UsersService.setRolePermission`; only permissions in `DELEGABLE_PERMISSIONS` can be granted, and keys still need `settings:secrets`.
- Knowledge search goes through `KbSearchService`; anything shown or said to a customer uses `audience: 'customer'` (approved public documents only). Embeddings are 1024-dimensional and the `embedding` role is pinned (ADR 0010). Knowledge connectors (ADR 0033, `apps/api/src/kb/connectors`) sync outside sources in the worker (`kb-sync` queue) through `KbConnectorsService.sync`, which writes documents only through `KbService` (`addFromConnector`, `updateFromConnector`; drafts unless the connector approves its own; gone items archived, never deleted). A new source type is a `ConnectorSource` in `sources.ts` that talks to the real service (`assertPublicUrl` unless `KB_CONNECTOR_PRIVATE_HOSTS` allows the host; folders only under `KB_CONNECTOR_PATHS`; databases read-only with a timeout and a row cap), with its settings in `kbConnectorConfigSchemas` and its credentials in `KB_CONNECTOR_SECRETS` (secrets `kb.connector-<id>.<field>`).
- Demos and tests use `apps/fake-providers` (scripted LLM, the sample "Demo Store systems" MCP server at `/mcp` with fictional orders) instead of real keys. Its refunds live in memory: `POST /demo-store/reset` clears them, and any `@shopper.example` address owns any `DS-9xxxx` order (fresh test customers). Don't add stand-ins for other external services there (decided 2026-10-01): build the real integration, unit-test it with `fetch` stubbed, and integration-test it through the real routes.
- WhatsApp (ADR 0015) lives in `apps/api/src/channels/whatsapp`; the files ported from whatsapp-crm keep their MIT header (`THIRD_PARTY_NOTICES.md`). The webhook is public, so it must verify the signature over `req.rawBody` before anything else, then queue the payload (`whatsapp-webhooks`); the worker processes it. Senders return the provider's message id and throw `PermanentDeliveryError` for failures a retry can't fix. Delivery reports go through `ConversationsService.applyProviderStatus` (statuses only move forward). Agent free text is refused outside the 24-hour window; templates go through `WhatsAppTemplatesService.prepare`. Read WhatsApp settings with `ChannelConfigService.whatsapp()` (never cached).
- Channel status lights (ADR 0016): the rules are pure functions in `apps/api/src/channels/health/health-rules.ts`; add a check there, with a unit test, when a channel gains a new way to fail. Reading the lights must not call outside services: live checks go through `ChannelConfigService.probe` (not audited; never automatic for paid APIs such as Sarvam), and processes share observations through `ChannelSignalsService` (Redis; losing them must be harmless). WhatsApp is connected through `WhatsAppConnectService`, which checks with Meta before it saves anything.
- Voice (ADR 0018) lives in `apps/api/src/channels/voice` and runs in the API process only (`VoiceModule`): a call is a `VoiceSession` owned by `VoiceService`. Speech goes through the `SpeechProvider` interface (`SarvamSpeech`); tests swap it with `VoiceService.useSpeech` and the scripted provider in `test/voice-double.ts`, never a fake Sarvam service. What the caller says goes through `InboundService.handle()`; the AI turn runs inline (`AiAgentService.runTurn`, not the `ai-turns` queue); spoken replies are stored `sent` with `message.spoken`, and a would-be draft is a handover. Recordings are read only through `VoiceCallsService.recording` (audited). The browser audio engine `voice-audio.ts` exists twice (`apps/chat-widget/src`, `apps/orbit-desk/src/features/voice`): keep the copies identical.
- Reports, ratings and the portal (ADR 0019):
  - "Who handled a ticket" has one definition (`HANDLED_BY` in `packages/shared/src/reports.ts`); reports, the CSV and ratings all use it. Report queries live in `apps/api/src/reports` (read-only, except the audit entry for an export).
  - Ratings are given by customers only (`CsatService.submit`, reached from the survey link, the chat socket or the portal). Never add a staff route that sets one, and never store a survey link where an agent can read it.
  - Portal routes are `@Public()` for the staff guard and protected by `PortalGuard`; they take the customer from the session, never from the request, and answer 404 for anything that isn't theirs. Portal replies go through `InboundService.handle()` with `ticket.id` set.
  - Links we email carry tokens from `common/signed-token.ts` (an id plus an HMAC, one purpose each). Mail the system sends by itself goes through `SystemMailer`, from the worker.
  - The AI resolves or closes tickets only through `AiAutoResolveService`, and only while it still owns them: the customer answers "anything else?" with a no (`declinesMoreHelp`, no model call), the customer stays quiet for the channel's quiet time (`closing.quietMinutes`, else `autoResolveHours`; never while an approval is waiting), and a ticket it resolved is closed for good after `closing.closeResolvedAfterDays`. `tickets.ai_closure` says why.
- Learning from ratings (ADR 0020) lives in `apps/api/src/learning`. Keep its two rules: on its own the system may only make the AI more careful (`LearningService.cautionFor` → rule `poor_feedback`, a draft instead of a send); what the AI says changes only through staff (lessons from `LearningService.lessonsFor`, or knowledge base drafts that still need approval). Never put customer-written text (rating comments, messages) into a lesson or the prompt's lesson block automatically. Lessons are part of the prompt: changing how they are injected needs a prompt version bump and a golden.
- Hardening (ADR 0021):
  - A new `@Public()` route or public socket event needs a limit: `@RateLimit({ name, limit, windowSeconds })` on routes, `RateLimiterService.hit` elsewhere. Take the caller's address from `req.ip` or `clientAddress()` (`common/client-address.ts`), never from `X-Forwarded-For` or `socket.handshake.address` directly.
  - Operational tables that grow get a `purge…(before)` method on their owning service and a line in `RetentionService.run`. Tickets, messages, customers and the audit log are never deleted there.
  - A new BullMQ queue gets a label in `QUEUE_LABELS` (`packages/shared/src/system.ts`) so its failed jobs show in Settings → System. That view shows identifiers only; never return a job's payload.
  - Work that crosses a process carries the trace: outbox events do by themselves; a new queue passes `currentTrace()` in the job data and wraps its processor in `withSpan`. Spans carry ids and route patterns, never URLs, bodies or message text.
  - Every customer message passes `screenInbound` in `ai/guard.ts` before any model sees it (ADR 0029): a strong jailbreak, abuse or spam hit warns or ends the conversation through `AiAutoResolveService.closeForConduct` (only where the AI answers by itself and the customer is reading; elsewhere a person gets it), and flags go through `CustomersService.flagInTx` (`customer_flags`, cleared by a person with a note, never deleted). A new pattern goes in `guard.ts` with a case that must not match (quoted text, a shop meaning). The AI is the first line: a person is brought in only for the reasons ADR 0029 lists, and a request for one gets an offer first (`handover.personRequestsBeforeHandover`). Answers that need no chat model (small talk, FAQ direct answers, the answer cache; ADR 0030) live in `AiFastPathsService` and still pass `assess()`. What the AI does with one customer message is decided by the turn plan (`ai/turn-plan.ts`): the closing check, the conduct, request-for-a-person and off-topic ladders, and the clarifying question, as a pure module (facts in, steps out; no database, model or clock). `AiAgentService.turn()` only gathers the facts and carries the steps out. A new per-message rule goes in the plan, with a case in `turn-plan.test.ts`; the strikes and counts it reports are saved in the reply's transaction (`apply()`), never before it.
  - The model's reply passes `decide()` in `ai/policy.ts` before use; a new kind of unsafe output gets a rule there, a unit test and a golden in `apps/api/test/evals/redteam.yaml`.
- Integrations (ADR 0022) live in `apps/api/src/integrations`. An outside app authenticates with an API key (`tms_sk_…`, stored as a SHA-256, returned once on creation: the one exception to "no route returns a secret"). Routes for integrations carry `@ApiKeyAuth()` and take the key from `@ApiKey()`; they refuse staff tokens, and every other route refuses keys, so never read `ctx.user` there and never add `@ApiKeyAuth()` to a staff route. A key's scopes come from `API_KEY_SCOPES` and are enforced by `@RequirePermission` like staff permissions. An integration route must only ever return data of the calling key's integration, and answer 404 for anything else. `IntegrationsModule` is imported by `AuthModule`: keep it free of modules that need authentication.
- The integration API (ADR 0023) lives in `apps/api/src/integration-api`. Tickets an app raises are channel `api` and go through `InboundService.handle()` like every channel; never write tickets or messages directly there. Each route loads the ticket through `IntegrationTicketsService.owned`, which answers 404 unless `tickets.integration_id` is the calling key's integration. What an app reads back is what the customer may see: no drafts, no notes. `externalRef` and `metadata` come from an outside system: Orbit Desk shows them as text, and the prompt gets them only through `ticketContext()` (bounded, inside `<ticket_context>`).
- Incidents (ADR 0024) are problems an app reports about itself through `POST /integration/events`. `IncidentsService.report` is the only writer of `incidents`: one transaction under a per-fingerprint advisory lock, opening the ticket with `InboundService.handleInTx` (`ai: 'off'`, `metadata.kind = 'incident'`, which the classifier skips). There is at most one open incident per integration and fingerprint. Counting a repeat (`occurrences`, `last_seen_at`) is a counter and is not audited; opening, the noted repeats (`INCIDENT_NOTE_AT`), a rise in severity and resolving are. A recovery resolves the ticket only when no person has acted on it (`AuditService.hasActor`; being assigned by a routing rule does not count), and reports never lower a priority.
- Webhooks (ADR 0025) live in `apps/api/src/webhooks`. To tell integrations about something new, add a public event name to `WEBHOOK_EVENTS` and map the domain event in `webhook-events.ts` (`toWebhookEvent`), with only ids and status keys in `refs`; then build its body in `WebhookPayloadService.data` from what the integration API would return. Never put customer text in `refs` or in the delivery log, and never send drafts, notes or staff-only fields. `WebhookDispatchHandler` only writes delivery rows and queues jobs; all sending happens in `WebhookDeliveryWorker` through `WebhookSender` (address checked on every send, redirects refused). The signing secret is `integration.wh-<id>.secret`, returned once on create and rotate. The delivery log is a log: not audited per row, purged by retention.
- Widget and branding (ADR 0026). The chat widget (`apps/chat-widget/src/widget.ts`) must keep working with no options: new behaviour is opt-in through `TMSChat.init` options, and anything a page passes (`theme`, `strings`, `context`, `visitor`) is untrusted input: validate it in the widget and again on the server (`chatHandshakeSchema`, `chatContextSchema`). With `anonymous: 'fresh'` a visitor without an identity token always gets a new conversation and a required name and email form, and nothing of theirs is stored in the browser. A chat session is resumed only by the person it belongs to (`ChatSessionService.open`: the stored token alone proves nothing after a sign-out), and on a web chat outside an integration tools act only for a visitor the chat vouched for (`boundEmail`), never for a typed email. A chat started with `integration` sets `tickets.integration_id`; its identity tokens are checked with `integration.<slug>.chat_identity` (falling back to `CHAT_IDENTITY_SECRET`), and a verified `sub` is the identity `integrationExternalId(slug, sub)`, the same as the API's `customer.externalId`. Customer-facing wording that names the company comes from `BrandingService` (defaults are the sample shop): never hard-code a company name, a sign-off or "order" wording in the help center, the widget or a prompt.
- The integration API is a public contract. When a route, a contract in `packages/shared/src/integrations.ts` or `webhooks.ts`, or the signing scheme changes, change with it: `packages/sdk` (its types are compared with `@tms/shared` in `sdk.test.ts`; `apps/api/test/sdk.int.test.ts` runs it against the real API), `docs/integration/examples/python/tms_support.py` (run `python -m unittest test_tms_support` in that folder), `docs/integration/signature-vectors.json` (both clients must reproduce it; never edit a vector to make a test pass) and the guide in `docs/integration/`. Document integration and webhook routes with `ZodBody`/`ZodQuery` (`common/zod-openapi.ts`) so `/docs` shows the schema the route validates.
- The Ethnic Threads demo (ADR 0027, ADR 0028) proves the integration API with an outside app, a demonstration shop. Keep it honest: the shop may simulate its own business (no money, nothing shipped, orders on a clock, the admin's switches for failing payments and a late carrier) and says so on its pages, but everything between the shop and TMS goes through the public integration API from the shop's own code: no hand-posted events, no edited timestamps, and never a field that collects a card number or other payment detail. TMS holds no code for that app, only data (`scripts/sample-data/garment/`: its knowledge base may say only what the shop really does). When the demo shows a gap in TMS, fix TMS for every integration rather than special-casing the app. Routing rules can match a tag (`conditions.tag`), which is how incident tickets reach an operations team.
- Tools and identity on an integration's tickets (ADR 0028): a tool with a `customerArg` runs there only for a customer the app has named, meaning an `external_id` identity `<slug>:…` from `customer.externalId` or a signed chat identity (`boundEmail` in `ai/ai-agent.service.ts`). Never bind a tool to an email a visitor typed. An email sent with `externalId` is stored verified, and `CustomersService.attachIdentity` moves an unverified email to the customer who proved it (audited); a verified email is never moved. `GET /integration/tickets?customer=` filters by the app's own id for a person.
- Channels produce a `MessageEnvelope` and call `InboundService.handle()`; outbound messages are stored `pending` and sent by the worker's `DeliveryHandler` (spoken voice replies are the exception). Don't send to external services inside a request.
- Worker services that hold resources stop in `beforeApplicationShutdown` (the DB pool and Redis close in `onApplicationShutdown`).

## Agent skills

### Issue tracker

Issues and specs live as GitHub issues in `BlackDeathWarrior/ticketing-sys`, through the `gh` CLI. See `docs/agents/issue-tracker.md`.

### Triage labels

The five default labels: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`. See `docs/agents/triage-labels.md`.

### Domain docs

Single-context: one `GLOSSARY.md` at the repo root (created when a term is first settled) and the decision records in `docs/adr/`. See `docs/agents/domain.md`.
