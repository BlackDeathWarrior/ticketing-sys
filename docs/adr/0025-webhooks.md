# ADR 0025: Webhooks to integrations

Status: accepted (2026-10-01)

## Context

An app that raised a ticket (ADR 0023) or reported an incident (ADR 0024) had to poll to learn what happened next: an agent's answer, a status change, an approval waiting. Polling is slow and wasteful, and nothing told an app's own backend about tickets from other channels at all.

TMS already has what webhooks need on the inside: every change writes a domain event to the outbox, and the worker runs handlers for it with retries.

## Decision

### Subscriptions

- A **webhook subscription** belongs to an integration: an address, the events it wants, a scope, on/off.
- **Scope** `own` (default) sends only what concerns the integration's own tickets and incidents. `all` sends every ticket in the workspace, whatever channel it came from; an admin chooses that deliberately, because it sends other channels' customer messages to the app.
- Managing them needs `integration:manage`; creating, deleting and rotating the secret also need `settings:secrets`.

### Events

A fixed public vocabulary, mapped from the internal domain events so those can change without breaking receivers:

`ticket.created`, `ticket.updated`, `ticket.status_changed`, `ticket.assigned`, `message.created`, `incident.opened`, `incident.updated`, `incident.resolved`, `approval.requested`, `approval.decided`, `csat.submitted`, and `ping` (tests only).

Drafts, internal notes, AI runs, tool calls and settings changes are never sent. `message.created` covers what the customer wrote and what was sent to them.

### What is sent

```json
{ "id": "<delivery id>", "type": "ticket.status_changed", "createdAt": "<when it happened>", "integration": "<slug>", "data": { "ticket": { … }, "from": "new", "to": "resolved" } }
```

- `data` holds what the integration API returns for the same records (`IntegrationTicketView`, `IntegrationMessageView`, `IncidentView`): no staff-only fields.
- The body is **built when it is sent**, from current records. The delivery log stores only identifiers and status keys (`refs`), never the body. So a retry or a redelivery shows the ticket as it is now, and customer text is not copied into a log that agents can read.

### Signing

- Header `X-TMS-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256>` over `<t>.<raw body>`, with the subscription's secret (`whsec_…`). `X-TMS-Event` and `X-TMS-Delivery` carry the type and the delivery id.
- A receiver recomputes the HMAC over the raw body, compares in constant time, and refuses a timestamp more than five minutes off (replay). `sign.ts` is ported from whatsapp-crm (MIT).
- The secret is generated by TMS, stored in the secret store (`integration.wh-<id>.secret`) and returned once, when the subscription is created or the secret is rotated: the same exception to ADR 0009 as an API key (ADR 0022). Rotation takes effect on the next send.

### Delivery

- `WebhookDispatchHandler` is one more domain-event handler. It only writes a delivery row per interested subscription and queues a job. It never calls a receiver, so a slow or dead one cannot hold up or fail the shared `domain-events` consumer (where one handler throwing retries them all).
- `WebhookDeliveryWorker` sends on its own queue, `webhook-deliveries`: `WEBHOOK_MAX_ATTEMPTS` attempts (8) with a doubling wait from `WEBHOOK_BACKOFF_MS` (5 s), `WEBHOOK_TIMEOUT_MS` (5 s) per attempt. Any 2xx is success. A redirect is a failure, not followed.
- The unique index `(subscription, event)` and the job id make dispatch idempotent when the event's handlers are retried.
- After the last attempt the delivery is `failed`. `WEBHOOK_DISABLE_AFTER` (15) failed deliveries in a row switch the subscription off, with the reason, an audit entry and a notification to people who manage integrations. Switching it back on resets the count.
- A failed or delivered entry can be **sent again** from the log: a new delivery row, queued through an outbox event, so nothing is sent inside a request. **Send a test** is the exception: one synchronous `ping`, like the channel and tool tests, logged but never retried and never counted.
- Delivery is at least once: a receiver should treat `id` as an idempotency key. Order is not guaranteed.

### Where TMS will call

- A public **https** address, checked on save and on every send (`assertPublicUrl`): no private, loopback, link-local or metadata addresses.
- `WEBHOOK_PRIVATE_HOSTS` lists hosts that may be private or use plain http: a local demo app, a compose service. The dev compose file allows `host.docker.internal`.

### What is recorded

- Creating, changing, deleting, rotating, an automatic switch-off and a redelivery request write audit and outbox rows.
- The delivery log itself is a log: rows and attempt counts are not audited or published (publishing them would feed back into the dispatcher). The same class of exception as `llm_calls` (ADR 0008). It is purged by retention (`webhookDeliveriesDays`, default 30); deliveries still waiting are kept.
- The log keeps an HTTP status and a short error of our own wording, never the receiver's response body.

### Orbit Desk

Settings → Integrations → an integration: a Webhooks card with the address, events, scope, state and last delivery; add (secret shown once), send a test, the delivery log with "Send again", switch off or on, rotate the secret, delete.

## Consequences

- A `message.created` for a message the app itself posted comes back to the app. Receivers that mirror messages should skip `data.message.from = "customer"` or dedupe on the message id.
- Because bodies are built at send time, a webhook for an event may describe a later state (a `ticket.created` whose ticket is already in progress). The type and `from`/`to` say what happened; the ticket shows where it is now.
- An event whose record is gone by the time it is sent fails for good, with the reason in the log, instead of sending an empty body.
- Attempts stop after about ten minutes with the defaults. A receiver that is down longer needs "Send again" or a poll of the integration API to catch up.
